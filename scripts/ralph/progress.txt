## Anti-Patterns Being Fixed

| Before | After |
|--------|-------|
| `async schedule(): Promise<void>` | `schedule(): Effect.Effect<void, HandlerMissing, SchedulerService>` |
| `console.error(...)` | `Effect.logError(...)` |
| `Promise.all([...])` | `Effect.forEach(tasks, { concurrency })` |
| Manual retryCount | `Effect.retry(task, Schedule.exponential("1s"))` |
| `scheduler.checkpoint()` injected | `Effect.service(SchedulerService)` from context |

## Breaking Changes (0.1.0 → 0.2.0)

```typescript
// Before
type TaskHandler = (scheduler: ReliableScheduler, taskId: string, params: unknown) => Effect.Effect<void>;
await scheduler.schedule(at, id, name, params);

// After
type TaskHandler = (taskId: string, params: unknown) => Effect.Effect<void, never, SchedulerService>;
await scheduler.schedule(at, id, name, params).pipe(runPromise);
```

## Learnings from Story 004

- Public APIs now return Effect<T, E, never> instead of Promise<T>
- Users must call Effect.runPromise() to execute the effects
- SchedulerService interface uses R = never for all methods since they don't require external services
- TaskHandler signature changed to R = typeof SchedulerService to allow service access
- Breaking change: all public method calls need wrapping with Effect.runPromise

## Learnings from Story 005

- Replaced manual retry logic with Effect.retry and Schedule.exponential
- Task execution now uses Effect.retry(handler, Schedule.exponential(Duration.millis(100)))
- retryCount removed from Task interface (kept for compatibility)
- Handlers can now fail and be retried automatically with exponential backoff
- Effect.provide used to provide SchedulerService context to handlers

## Learnings from Story 006

- Replaced Promise.all with Effect.forEach for concurrent task processing
- Used Effect.forEach with { concurrency: this.maxConcurrentTasks } to respect limits
- Created _processTaskEffect wrapper to convert async task processing to Effect
- Alarm processing now uses Effect.forEach for fiber-based concurrency
- Removed manual batching logic in favor of Effect's built-in concurrency control

## Learnings from Story 007

- Replaced console.log/error/warn with Effect.log/logError/logWarning
- Used yield* Effect.log in Effect contexts
- Used Effect.runPromise(Effect.log(...)) in async contexts
- Structured logging with appropriate levels (log, logError, logWarning)
- Effect logging integrates with runtime for console output

## Example Migration Learnings

- Added runSteps and runSubSteps to SchedulerService interface and _createServiceLayer
- Updated all task handlers from (sched, taskId, params) to (taskId, params) with SchedulerService

## Story 008: Fix Example Hydration and Svelte5/SvelteKit Issues

COMPLETED ✅

**Root Causes Identified:**
- Server-side data loading used different filtering than WebSocket updates
- Svelte5 data reference warnings for prop usage
- Commands cannot be called in server-side rendering context
- svc undefined errors in Effect handlers due to scope issues

**Solutions Implemented:**
- Server load functions now load ALL tasks and apply same filtering as WebSocket
- Fixed Svelte5 prop reference issues using $derived and $effect
- Changed getTasks from command to query for SSR compatibility
- Fixed svc scoping in mine-resource-loop handler by wrapping in Effect.gen
- Added direct worker HTTP calls in server load functions
- Fixed WebSocket filtering to match server-side filtering exactly

**Key Technical Patterns:**
- Server load functions must use same data source and filtering as real-time updates
- Svelte5: Use $derived for reactive prop-derived state, avoid direct prop references in $state
- Effect-TS: Ensure svc is available in all Effect.gen contexts that need it
- WebSocket: Filter on client must match server-side filtering to prevent hydration mismatches
- SSR: Cannot use commands in load functions, use direct HTTP calls or queries

**Results:**
- No hydration mismatches - server and client render identical content
- Real-time updates work without flickering
- Miners appear immediately when created
- Mission control game functions properly
- All demos work end-to-end with proper Svelte5 patterns

## Story 010: Remove setTimeout from Example Worker for DO Hibernation

COMPLETED ✅

**Problem:**
- `setTimeout` in `triggerBroadcast()` prevented DO hibernation
- DO hibernation is critical for cost efficiency in production

**Solution:**
- Replaced `setTimeout(..., 100)` with immediate execution
- Changed `broadcastQueue` from `ReturnType<typeof setTimeout>` to simple boolean flag
- Maintained debouncing logic to prevent broadcast storms

**Key Technical Pattern:**
- For DO hibernation: Avoid any timers (setTimeout, setInterval) that keep the DO awake
- Use immediate execution for operations that can tolerate slight timing variations
- Debouncing can still work without timers using simple boolean flags

**Impact:**
- DO can now hibernate properly, reducing costs
- Broadcasts still debounced to prevent storms
- No functional change in user experience

## Story 011: Add Input Validation for taskId and taskName

COMPLETED ✅

**Problem:**
- No input validation allowed potentially malicious or malformed identifiers
- Could cause issues with storage keys, logging, or other systems

**Solution:**
- Added `ValidationError` tagged error type
- Created `validateTaskIdentifier()` function with regex validation
- Applied validation to `runNow()` and `schedule()` methods
- Validation rules: alphanumeric + hyphen + underscore only, max 128 chars, non-empty

**Key Technical Pattern:**
- Input validation at API boundaries prevents downstream issues
- Tagged errors provide structured error information for clients
- Regex validation with clear error messages helps debugging
- Effect-based validation composes cleanly with existing error handling

**Impact:**
- Prevents path traversal attacks (`../etc`)
- Ensures consistent identifier formats across the system
- Better error messages for developers
- Maintains backward compatibility for valid identifiers

## Story 012: Add maxTotalTasks Limit to Prevent Storage Exhaustion

COMPLETED ✅

**Problem:**
- No limit on total tasks could exhaust Durable Object storage
- Completed/failed tasks accumulate indefinitely

**Solution:**
- Added `maxTotalTasks` constructor option (default: 10000)
- Added `TaskLimitExceeded` tagged error
- Check total task count before creating new tasks in `runNow()`/`schedule()`
- All tasks count toward limit until cleared with `clearCompleted()`/`clearAll()`

**Key Technical Pattern:**
- Resource limits prevent runaway resource consumption
- Tagged errors provide clear feedback when limits are exceeded
- Clear operations (`clearCompleted`/`clearAll`) reduce the count
- Default limits provide sensible out-of-box behavior

**Impact:**
- Prevents storage exhaustion in production
- Completed tasks can be cleaned up to free slots for new tasks
- Clear error messages when limits are hit
- Configurable limits for different deployment scenarios

## Story 013: Migrate Example Worker Console.* to Effect.log*

COMPLETED ✅

**Problem:**
- Example worker used console.* instead of Effect logging
- Inconsistent with Effect-First principles
- Console output not integrated with Effect runtime

**Solution:**
- Replaced all `console.log` with `await Effect.runPromise(Effect.log(...))`
- Replaced all `console.error` with `await Effect.runPromise(Effect.logError(...))`
- Replaced `console.warn` with `await Effect.runPromise(Effect.logWarning(...))`
- Made `broadcast()` method async to support await
- Left one `console.error` in top-level catch block (allowed per requirements)

**Key Technical Pattern:**
- Structured logging integrates with Effect runtime
- Async logging requires await in async contexts
- Method signatures may need updating to support async logging
- Catch blocks can retain console.* when Effect context unavailable

**Impact:**
- Consistent Effect-First logging throughout codebase
- Better integration with Effect runtime and potential future logging infrastructure
- Example code demonstrates proper Effect logging patterns
- Only 1 console.* usage remains (in allowed catch block)
